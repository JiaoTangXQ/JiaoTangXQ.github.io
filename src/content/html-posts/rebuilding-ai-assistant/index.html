Case Study

重构 AI 助手，实践中的一些思考

这次重构不是为了追新版。真正的问题是：一个已经接入日常聊天、定时提醒和长期记忆的 AI 助手，怎么在不中断使用的情况下迁移到新架构，并且让新功能真的改善使用，而不是只增加复杂度。

我先问的不是“能不能升级”

最开始我关心的是上游新版到底改了什么。不是每个更新都值得合并，尤其是一个已经在日常使用的 [[AI 助手]]。它不是玩具项目，一旦迁移失败，影响的是每天的提醒、聊天、账号状态和历史记录。

所以第一个问题不是“新版好不好”，而是“哪些新功能对我有用”。我让 AI 帮我看上游变化，重点看三件事：它有没有更好的多账号架构，有没有更可靠的队列和容器隔离，有没有给未来接入不同模型留出位置。

这个判断很实际。一个功能只有在改变使用结果时才算有价值。比如“支持更多 provider”本身不是目的；它有价值，是因为以后可以在 [[Claude Code]]、[[Codex]] 或其他本地/云端工具之间切换，而不是把整个系统绑死在一种调用方式上。

迁移必须先保护正在使用的版本

我没有直接在原来的目录里改新版。第一条规则是单独开一个新目录，让新版可以构建、迁移、启动和测试，但不影响旧版继续工作。

这听起来只是工程习惯，实际上会改变心态。如果新旧版本在同一个目录里纠缠，我会下意识急着修补，把迁移变成一串临时操作。放到独立目录后，事情变成了可验证的流程：先拷贝数据，再迁移，再启动新服务，再验证，再决定切换。

这里有一个我现在更看重的原则：AI 可以帮我写脚本、跑检查、读日志，但它不能替我承担破坏性操作的后果。迁移这种事必须保留回滚路径。旧服务什么时候停，新服务什么时候接管，数据快照在哪里，失败后怎么退回，都要先写清楚。

我不想为了新版丢掉旧聊天

新版架构更干净，但干净不等于可以扔掉历史。这个助手已经在多个聊天渠道里用了一段时间，账号、群组、定时任务、会话状态和聊天记录都属于实际使用的一部分。

迁移时我把数据分成几类看：

  • 身份和路由。哪个聊天入口对应哪个 agent，哪些用户有权限，哪些账号启用。
  • 运行状态。当前会话、待处理消息、定时任务、容器状态。
  • 长期资料。每个 agent 的本地工作区、记忆文件、用户偏好和任务文件。
  • 历史记录。旧聊天和任务日志不一定每次都进 prompt，但必须能保存和查询。

这也是我对 [[Agent]] 系统的一个看法：聊天历史不是装饰。它不一定要全部塞进上下文窗口，但它应该有可追溯的位置。否则升级只是把软件跑起来了，使用连续性其实断了。

Claude Code 额度和 API key 是两个不同问题

迁移中我一直问一个问题：新版还能不能直接接入 Claude Code？能不能继续用订阅额度，而不是强制我改成 API key？

这个问题不是省钱这么简单。Claude Code 代表一套已经在本地工作流里跑通的会话方式。它有自己的续聊状态、工具调用、文件系统上下文和 compact 行为。如果迁移后只能走 API key，整个体验会变成另一个系统，旧的会话连续性和本地使用习惯都要重新评估。

后来我把 provider 看成系统边界，而不是模型名称。Claude Code、Codex、其他 CLI 或 SDK 都可以是 provider。真正要做的是让消息队列、工作区、记忆文件和 provider 之间的接口稳定。这样将来换模型，不必重写整个聊天平台。

“能启动”不等于“能用”

新版启动后，第一次真实测试就暴露了一个很典型的问题：服务在跑，聊天平台也连接了，但用户发消息没有收到回复。

如果只看表面，很容易误判成平台回调问题、权限问题或模型问题。实际排查要顺着消息走：消息有没有进路由，路由有没有进会话队列，队列有没有唤醒容器，容器有没有正常启动，agent 有没有写出回复，回复有没有被投递回聊天平台。

最后问题出在运行镜像没有构建好。消息已经进来了，队列也在唤醒，但容器启动失败。修好镜像后，之前 pending 的消息继续被处理，回复才发出去。

这件事让我再次确认：AI 助手这种系统不能只验证“进程活着”。要验证的是一整条用户路径：用户发一句话，agent 看见，模型处理，工具能调用，消息能送回去。中间任何一段断掉，用户看到的都是“它没回我”。

记忆不是一个功能开关

迁移完成后，又出现了一个更真实的问题：有人反馈 agent 记性不太好，上午说过的事，下午还会问。

这句话很重要。因为它不是系统级故障，而是体验级故障。数据库在，聊天记录在，Claude 会话也在，但用户仍然觉得它忘了。原因是“历史存在”和“当前回答会用到历史”之间还差一层设计。

我把记忆拆成几层：

  • 短期记忆。模型当前会话和续聊状态，适合处理连续对话。
  • 工作记忆。当天任务、完成状态、未完成承诺，适合给定时提醒使用。
  • 长期记忆。用户偏好、长期目标、固定规则，适合写进稳定文件。
  • 冷历史。旧聊天归档，适合需要时检索，不适合每次塞进 prompt。

问题出在工作记忆。用户早些时候汇报过进度，模型当时是知道的；但几个小时后的定时任务仍然按模板问“今天完成了什么”。这不是缺少更多上下文窗口，而是缺少一个当天状态文件。

我最后没有急着上向量检索

遇到记忆问题，最容易想到的是 RAG、向量库、语义检索。但这次我没有先做这个。

原因很简单：这个问题不是“找不到三个月前说过的一句话”，而是“今天下午不要忘记上午已经完成的事”。用向量检索解决当天 checklist，反而会把问题做复杂。

更合适的第一步是给每个 agent 一个当天 journal。用户说“做完了”“改到一半”“今晚要做某件事”时，agent 把它写进当天文件。定时任务触发前先读当天 journal 和近期计划。已完成的打勾，未知的再问。

这就是 [[记忆系统]] 里很普通但有用的一条规则：不同时间尺度用不同介质。当天状态用 journal，长期偏好用 profile，历史对话用 archive，语义检索以后再加。

Prompt 不能替代工程边界

我当然可以直接给 agent 加一句提示：“不要忘记用户说过的话。”这类提示很容易写，也很容易失效。

更可靠的做法是把规则放到系统结构里。比如定时任务格式化时，自动附上一段 memory check：发送提醒前先读当天 journal 和近期计划；已完成的事项不要再问。这样不是指望模型永远自觉，而是让每条定时任务都带着同一个操作约束。

同时，agent 的总指令也要改。用户汇报实质进展时，应该更新当天 journal；稳定偏好才写长期文件；普通闲聊不要变成永久记忆。这个边界如果不写清楚，记忆系统会从“帮我记住”变成“什么都往里塞”。

AI 协作里，人要保留判断权

这次重构里，AI 做了很多事：读上游代码、比较功能、写迁移计划、改测试、查日志、解释运行状态、设计记忆修复方案。它确实能把工程推进得很快。

但真正需要人判断的地方没有减少。我要判断哪些上游功能值得合并，什么时候停旧服务，哪些聊天历史必须保留，Claude Code 和 API key 的差别是否影响体验，记忆问题应该先用 journal 还是先上检索。

我现在更倾向于把 [[Codex]] 和其他开发 agent 当成“会动手的审稿人”。它可以提出方案，也可以实现方案，但我必须不断追问证据：日志在哪里，数据库里有没有记录，测试跑了什么，失败是新问题还是旧债，用户看到的路径有没有真的变好。

AI 可以帮我执行，但不能替我定义什么叫“对用户有用”。

隐私不是发布前才处理

这个项目天然包含很多不能公开的东西：聊天账号、用户称呼、具体日程、聊天原文、本地路径、服务标识、数据库内容。写这篇记录时，我也不能把开发过程原样贴出来。

我保留的是结构和判断：多账号、消息队列、容器、provider、迁移、记忆层、定时任务。被拿掉的是能识别个人、账号、目录、服务名、具体聊天内容的细节。

这也是我对 [[本地优先]] AI 助手的看法：越贴近日常生活，越要把隐私边界当成工程边界。不是“发布时打码”就够了，而是从日志、文件命名、迁移报告、博客写作开始，就不要把不该公开的信息当作素材。

这次重构留下来的规则

如果把这次实践压缩成几条规则，我会留下这些：

  • 不要为了新版而升级。先问它改变了哪个使用结果。
  • 迁移先隔离，再验证，再切换。旧版本要能随时回去。
  • 聊天历史不必全部进上下文，但必须保存到能查询的位置。
  • 模型接入要做成 provider 边界，不要把系统绑死在一个调用方式上。
  • 记忆要分层。当天状态、长期偏好、冷历史不是同一种东西。
  • 定时任务要读状态再发问，否则它会像一个不看记录的助理。
  • AI 能帮我写代码，不能替我决定什么才算体验变好。

我做这个助手，不是为了得到一个更会聊天的机器人。真正想要的是一个能接住日常事务、知道边界、能持续迁移和修正的个人系统。它需要模型能力，也需要工程约束；需要记忆，也需要知道哪些东西不该记。
