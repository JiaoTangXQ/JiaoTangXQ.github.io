让 AI 写 HTML 笔记，而不是 Markdown 长文

我以前默认让 AI 输出 Markdown，因为它轻、好改、能进 Git。但最近这个默认选项开始动摇：当大部分内容都由 [[AI]] 生成，我负责审阅、判断和继续追问时，HTML 反而更适合承载复杂解释。

触发点是一篇 Claude Code 实践文章

Thariq 写了一篇 关于用 HTML 替代 Markdown 输出的文章。它打动我的地方不在“网页更好看”，而在一个工作流变化：很多文件已经不是人手写出来的，而是 agent 为了说明、规划、评审和分享生成出来的。

如果文件主要由人写，[[Markdown]] 的优势很明确：语法少、diff 清楚、编辑成本低。如果文件主要由 [[Agent]] 写，人只是读、选、批注、让它继续改，Markdown 的最大优势就变弱了。

我真正关心的问题变成另一个：AI 生成的内容，怎样更容易被人读懂、审查、比较和复用。

Markdown 的问题不是表达不了，而是读者很快会放弃

Markdown 能写标题、列表、代码块和表格。问题是，当 AI 开始生成一百行以上的计划、调研、PR 说明和代码解释时，它很容易变成一整面文字墙。

我自己也有这个问题：短 Markdown 我会读，长 Markdown 我往往只扫标题和列表。它看起来完整，但很难让我快速判断哪里是结论、哪里是证据、哪里是风险、哪里只是模型为了显得周全补出来的段落。

AI 还会在 Markdown 里做一些勉强的表达：用 ASCII 画图，用文字描述颜色，用缩进模拟流程，用一堆列表模拟状态机。这些内容能看，但不适合快速审阅。

HTML 把说明文变成可审阅的界面

[[HTML]] 的价值不是装饰，而是它能把不同类型的信息放到合适的位置。文字继续解释，表格负责比较，SVG 负责关系，代码块负责局部证据，折叠区负责隐藏细节，按钮负责导出结果。

内容类型 Markdown 常见结果 HTML 更适合的表达
方案比较 长列表，读者要在脑子里逐项对应差异。 并排卡片、对照表、按风险或成本标色。
代码评审 贴 diff，再写几段解释。 渲染 diff，在行旁边标注风险、原因和建议。
流程解释 编号列表或 ASCII 图。 SVG 流程图、状态机、数据流图。
设计探索 文字描述多个版本。 六个方案放同一屏，直接比较密度、语气和布局。
参数调整 让读者复制数字再改 prompt。 滑块、开关、预览和“复制为 prompt”按钮。

这会改变审阅方式。读者不必从头读到尾，而是先看第一屏结论，再点开图表、代码、风险和例子。复杂内容不再靠耐心硬撑，而是靠结构降低阅读成本。

好处来自四件具体的事

第一是信息密度。HTML 能同时放文本、表格、图、代码、图片和交互。很多原本需要几屏文字解释的内容，可以变成一个流程图加几条注释。

第二是可读性。AI 写长文时，最容易失败的地方不是没有内容，而是内容没有层次。HTML 可以把结论、证据、细节和附录分开，让读者按自己的目的跳读。

第三是分享。一个 HTML 文件上传到对象存储、GitHub Pages 或内部静态站后，别人点开链接就能读。Markdown 常常还需要平台渲染、附件下载或额外说明。

第四是双向交互。HTML 不只展示结果，还能收集人的选择。比如拖动 Linear 卡片重新排序，最后复制出 Markdown；调动画参数，最后复制成 JSON；编辑 prompt 模板，右侧实时预览三个样例。

真正的流程不是“生成一个漂亮网页”

如果只对 AI 说“做一个 HTML 页面”，它可能会生成一个装饰过度的静态页面。更好的要求是让它先理解任务，再选择表达方式。

  1. 先说清楚读者是谁，以及读者看完要能判断什么。
  2. 让 AI 读取材料：代码库、Git 历史、PR diff、网页、数据文件、截图、Slack 或 Linear。
  3. 让 AI 先设计信息结构：结论、主线、例子、图表、风险、FAQ、附录。
  4. 让 AI 生成单文件 HTML，样式、SVG 和少量交互都放进去。
  5. 让 AI 用浏览器打开检查，修正文字溢出、重叠、移动端布局和按钮行为。
  6. 把最终 HTML 当作审阅物，而不是把它当成 AI 输出的终点。

这里的重点是工具使用。[[Claude Code]] 这类工具能读文件系统、跑命令、看 Git diff、打开浏览器、截图检查。HTML 正好把这些上下文整理成一个人能读的界面。

我会这样下指令

我不会只给主题。我会把读者、材料、结构和验收标准都写进去。

请生成一个自包含 HTML 文件，用来解释：[主题]。

目标读者：[读者背景]
读者看完后必须能回答：
1. [问题一]
2. [问题二]
3. [问题三]

请先读取这些材料：
- [文件/目录/链接/PR/数据源]

页面要求：
1. 不要输出 Markdown。
2. 第一屏给出结论和导航。
3. 用 SVG 画流程图或结构图。
4. 用表格对比主要方案或概念。
5. 对能说明问题的代码片段做行内注释。
6. 细节放进可折叠区域，避免主线过长。
7. 如果有可调参数，做成滑块、开关或输入框。
8. 如果需要把结果交还给 AI，加入“复制为 Prompt/JSON/Markdown”按钮。
9. 所有样式和脚本都写进单个 HTML 文件。
10. 生成后用浏览器检查并修正布局问题。

这段 prompt 的作用不是限制 AI 的创造力，而是把产物从“文章”推向“解释工具”。如果主题是 PR 评审，它就应该渲染 diff。主题是配置调整，它就应该变成表单。主题是设计探索，它就应该并排展示多个版本。

所有东西都可以让 AI 生成，但审阅权不能交出去

Thariq 的文章里有一个容易被误解的点：既然 HTML 由 AI 生成，人是不是只负责欣赏结果。我的判断相反。HTML 的目标是让人更容易介入，而不是让人退出。

Markdown 长文的问题是人会跳过细节。HTML 做得好，反而会让人更快发现问题：数据流画错了，状态少了一种，代码标注和 diff 对不上，方案比较遗漏了失败条件，交互导出的 JSON 不能直接用。

所以我会把人的职责放在三个地方：定义阅读目标，检查事实和边界，决定下一轮让 AI 改什么。生成、排版、画图、浏览器检查可以交给 AI；判断不能外包。

代价也要算进去

HTML 不是所有场景的答案。它生成更慢，原文估计大约是 Markdown 的 2 到 4 倍。HTML diff 也更吵，代码评审时不如 Markdown 清楚。页面如果没有设计约束，还可能变成一堆颜色、阴影和卡片。

所以我会保留几条边界：

  • 需要频繁手改的纯文字内容，继续用 Markdown。
  • 需要严肃 code review 的规范文档，优先用 Markdown 或结构化文本。
  • 只是临时记录一句判断，不要为了形式生成 HTML。
  • 面向别人阅读、需要图表和比较的内容，优先考虑 HTML。

还有一个实践问题：要让 AI 写出符合自己品味的 HTML，最好给它一个参考文件。可以让它读取你的站点、设计系统或几篇你满意的 HTML 文章，再要求它沿用同一套排版和交互习惯。

我得到的判断

当内容由人手写、机器只是保存时，Markdown 是合适的默认格式。当内容由 AI 生成、人负责审阅和决策时，HTML 更像一个工作界面。

它让 AI 不只输出文字，还能输出图、表、对比、代码注释、参数面板和导出按钮。它让读者不只阅读，还能选择、调参、复制结果，再把修改后的上下文交回给 AI。

这套做法的价值不在“更像网页”。它真正改变的是人与 AI 的协作位置：AI 负责把复杂材料组织成可检查的界面，人负责判断这个界面有没有把问题讲清楚。
