触发点：agent 只能读到聊天里那点上下文

起点来自一个更直接的问题：我每天写在 Get 笔记里的内容，agent 读不到。它能处理我当前贴出来的文本，却不知道我过去记录过什么、删过什么、哪些想法已经出现过几次。[[Obsidian]] 进入这套系统，是因为它能把笔记变成本地文件。

这让我重新看待 [[个人知识管理]]。过去我按软件分工：记录放 Get 笔记，搜索和图谱放 Obsidian，和 AI 的讨论留在聊天窗口。每个工具都保存了一段上下文，但这些上下文没有自然汇合。结果是我每次问 agent，都要重新解释背景。

维护漂亮笔记库排在后面。我的目标是让自己的数据成为 agent 可以读取的长期工作上下文。

从这个目标往回推，工具选择就变了。我开始关心数据能不能导出，能不能本地保存，能不能被脚本处理，能不能保留来源。功能多不多排在后面。

第一条边界：Get 笔记是源头，Obsidian 是本地镜像

我的记录入口仍然是 Get 笔记。它负责捕获语音转写、网页、片段记录和日常想法。Obsidian 在这套系统里不承担主编辑器角色，它承担本地镜像、检索界面、图谱展示层和 [[Agent]] 可读取的文件系统。

这条边界很早就要定下来。否则本地 Markdown 一旦被手动改写，就很难判断哪一份才是事实。最终规则是：Get 笔记是 source of truth，Obsidian 里的原始层只同步，不手改。

  • Get 笔记：负责新增、修改、删除原始记录。
  • Obsidian vault：保存本地 Markdown，用于搜索、图谱和备份。
  • Agent：通过文件系统或 [[MCP]] 读取 vault，用这些文件回答问题、总结和生成派生关系。

一份备份解决不了这个需求。同步必须能处理新增、修改和删除；本地文件不能污染源头；AI 加工结果不能混进原始记录；agent 读取时要知道哪些目录可信，哪些目录只是派生判断。

目录分层：原始层只保存事实，派生层允许重建

最后形成的 vault 结构是三层：原始层、归档层、派生层。

vault/
  10_GetNote_Raw/                 # Get 笔记原始镜像，只同步，不手改
  30_AI_Derived/graph/            # 规则或 AI 生成的主题、概念、项目索引
    topics/
    concepts/
    projects/
  90_Archive/GetNote_Deleted/     # 远端已删除，本地保守归档
  00_System/getnote_sync_state.json

这层结构解决了一个容易被忽略的问题：原始内容和 AI 解释不能混在一起。原始层负责保存事实，派生层负责生成关系。同步脚本可以覆盖原始层，agent 可以重建派生层，两个动作互不污染。

这也是我后来判断 [[数据孤岛]] 的标准：如果数据只能被某个软件显示，不能被脚本读取和重建关系，它仍然被困在软件边界里。如果数据变成普通文件，并且来源、删除、派生关系都有位置，它才开始适合给 agent 使用。

第一版图谱骗过了眼睛

同步跑通后，我很快遇到另一个问题。最初脚本给每篇笔记写了 tag/...、topic/...、source/... 这类索引链接。Obsidian 图谱看起来很密，但密度来自标签星状图，不来自内容之间的引用。

这种结构不能算 [[知识图谱]]，只是很多笔记连到同一批空白索引页。它的后果是误导判断：我会以为知识关系已经形成，实际上只是链接数量增加了。

处理方式是删掉这些空白 tag、topic、source 页，并停止生成 Relations 段落。删完后图谱一度变成散点，这反而更接近事实：原始笔记之间没有天然链接。

后来的派生图谱没有写回原始笔记，而是放进 30_AI_Derived/graph/。第一版先不用大模型，只用标题、tags、topics、source_url 做规则聚合。结果是 345 篇原始笔记被聚成 7 个主题页、32 个概念页、3 个项目页。

删除策略必须保守

远端删除的笔记，本地同步后没有直接消失，而是进入 90_Archive/GetNote_Deleted/。一开始这看起来像没删干净，但直接删除风险更高：API 分页异常、QPS 中断、状态文件损坏都可能让脚本误判远端缺失。

所以默认策略改成归档。需要清理时，用显式命令处理空白笔记、测试笔记和无内容笔记。默认动作保留数据，需要破坏性清理时再单独触发。

这个规则也限定了 agent 的权限。agent 可以读原始层，可以写派生层，但不应该随手改原始层。原始数据保守，派生数据可以激进，因为派生层删掉还能重建。

最后收敛成一条命令

日常使用不能靠记一组步骤。最后同步和派生图谱重建被合成一个命令：

python3 tools/getnote_sync.py \
  --vault "$OBSIDIAN_VAULT" \
  sync-all \
  --force-full-rescan \
  --max-api-calls 1000

这条命令做三件事：

阶段 行为 原因
同步原始层 更新 10_GetNote_Raw/ 保留 Get 笔记里的事实内容，不做 AI 加工。
处理删除 远端缺失的笔记进入 90_Archive/ 避免 API 或状态异常造成误删。
重建派生层 生成 30_AI_Derived/graph/ 让关系来自可重建的派生判断，避免污染原始笔记。

跑完后，系统里有 345 篇 Get 笔记原始镜像、42 个派生图谱页、0 个空白 tag 索引页。这个结果比一张很密的图谱更有用，因为每个派生页都能追到原始笔记，错了也知道删哪里。

先别急着上 RAG

我一开始也会自然想到向量化、Claude Context、MCP、RAG、自动聚类。但这件事的第一阶段不需要先做完整检索系统。先把数据流打通，把原始层和派生层分开，把删除策略定清楚，后面的智能层才有可审计的输入。

向量检索适合召回，Markdown 适合保存和审计。两者可以并存，但向量库不应该替代文件层。否则我只是把数据从一个软件孤岛搬进另一个黑箱。

下一步我会做三件事：给派生页增加摘要；在不替代文件层的前提下接入向量检索；让 agent 只写派生层，不写原始层。

我得到的判断

这次改造给我的结论很具体：AI 时代的个人数据系统，起点应该是把自己的数据整理成 agent 能读取、能追溯、能重建关系的本地文件系统。换笔记软件和搭 RAG 都要排在这个动作后面。

Get 笔记继续负责记录，Obsidian 负责保存和查看，agent 负责读取和生成派生层。只要这三个角色不混，系统就能持续扩展；一旦原始记录和 AI 加工混在一起，后面所有自动化都会变得难以审计。

我现在判断一个工具是否适合进入这套系统，只问几个问题：它能不能导出，能不能本地化，能不能被脚本处理，能不能保留来源，能不能让 agent 在明确权限下读取。答不上来，就暂时不把长期数据交给它。
